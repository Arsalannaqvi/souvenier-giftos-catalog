# Brand Catalog Audit

Consolidates four ad hoc audits run this way already (Samsonite, Goblin,
Magnus Eco, the TTH→Botanica relabel — see `reference.md`'s calibration
log) into one repeatable recipe, so the next one doesn't get re-invented
from scratch or skip a step one of the earlier ones caught the hard way.

**Scope:** this repo's `data/products.json` + `data/brands.json` (the
public catalog site), not the Notion-based internal workspace. If the
brand also needs fixing in Notion, that's `Gifting-automation`'s
`gifting-catalog-manager` skill's job, separately.

## Trigger conditions

- Owner explicitly asks to audit/cross-check/verify a brand against its
  real site or catalog.
- **Or**, no one asked — but while doing something else, a product's own
  stored image/spec sheet/description names a brand different from what
  `data/brands.json` has it as. Stop the other task, don't guess or
  silently "fix" it: this is the project's brand-vs-competitor "stop and
  ask" rule applied to brand *identity*, not just brand-vs-competitor.
  Surface it to the owner and wait for confirmation before relabeling —
  see the TTH→Botanica entry in `reference.md` for exactly this case.

## The data model, in brief

- `data/brands.json` is a flat `{productId: brandName}` map — **a
  separate source of truth from the brand name embedded in the product's
  own `name` string** in `data/products.json`. Fixing a brand means
  checking both: the mapping (always) and the `name` string (if it also
  says the wrong thing). Missing either leaves a stale value visible
  somewhere. Full data model: this repo's `CLAUDE.md`.
- Brand pages (`brand/<slug>/`) are generated by
  `scripts/generate_brand_pages.py`, which wipes and regenerates the
  whole `brand/` directory from `data/brands.json` + `data/products.json`
  every run — nothing to clean up by hand there once the data is right.
- The homepage brand slider/chip list is **hardcoded in `index.html`**,
  not generated — a brand removal needs a manual edit there too.
- `scripts/generate_product_pages.py` bakes each product's "related
  products" list in at generation time, computed from array
  position/category — removing or adding products shifts those
  positions catalog-wide. Re-run it after any addition/removal, not just
  for the products you touched directly.

## The recipe

### 1. Enumerate
Count every current catalog entry for the brand (`grep`/`jq` over
`data/brands.json` for the brand name, or query `data/products.json`
filtered by the id prefix if the brand only uses one category). Note the
category breakdown — it's needed later to judge whether removing/hiding
a whole category leaves it empty (as happened with Goblin's Backpacks
and Magnus Eco's Sustainable category).

### 2. Check sources, in priority order, exhaustively
1. **The brand's official site.** Walk every category/listing page and
   record real page counts (e.g. "bags 56/56, backpacks 48/48") rather
   than relying on a site search box — a search miss is not proof of
   "discontinued," only a full category walk is. This is what separated
   Samsonite's 5 genuinely-discontinued lines from a false negative.
2. **A PDF/Excel catalog from the brand**, if one exists or the owner
   can supply one — check it *before* concluding a product is gone
   everywhere. Goblin's Elegance Tote Bag wasn't live but was in the
   current PDF catalog, so it was kept (photo cropped from the PDF,
   self-hosted under `assets/products/` since there's no live URL to
   host it externally).
3. Third-party marketplace listings are supplementary signal only
   (confirms a real product exists / genuine photo), never sole proof a
   product is still sold by this brand.

### 3. Classify each product
- **Live & accurate** — no change.
- **Live but stale** — update price/photo/description/dimensions from
  the real listing. Never fabricate a value for a field the live
  listing doesn't show.
- **Not live, found in a PDF catalog** — keep; self-host an image
  cropped from the PDF if there's no live URL to source it from.
- **Confirmed absent from BOTH the site (full category walk) and any PDF
  catalog** — removal candidate. Never remove on the strength of one
  source alone.
- **Wrong-brand attribution found** (the product's own stored image/
  spec sheet says a different brand) — stop, flag for the owner, apply
  only after explicit confirmation. Never auto-relabel.
- **Price is ambiguous between MRP and the catalog's stored "price"
  field** — flag for the owner rather than guess which one it is
  (Samsonite's Openroad 2.0 case: live MRP was confirmed, but the
  catalog's own "price" field doesn't reliably track MRP for sibling
  products, so filling it in would risk conflating the two).

### 4. Apply
- **Updates**: edit `data/products.json` (and `data/brands.json` if the
  brand mapping itself was wrong). Regenerate both
  `scripts/generate_product_pages.py` and
  `scripts/generate_brand_pages.py` afterward — editing the JSON alone
  does nothing to the already-baked static pages.
- **Removals**: delete the product(s) from `data/products.json` and
  `data/brands.json`, then also check, in order:
  1. Does this empty out a category? Confirm it drops from Browse
     Categories correctly after regeneration.
  2. Is the brand now gone entirely? Remove its hardcoded chip from the
     homepage brand slider in `index.html` — the generator won't do this
     for you.
  3. Regenerate `generate_product_pages.py` for the *whole* catalog, not
     just the touched products — removing items shifts "related
     products" array positions everywhere.
  4. If any touched JS file's content changed, bump its `?v=` cache-bust
     query string (see `CLAUDE.md`) — otherwise a cached browser keeps
     running old JS.
- **Relabels**: after owner confirmation, update `data/brands.json`'s
  mapping and, if the product's own `name` string also carries the old
  brand, that too. Regenerate both generator scripts; the old brand's
  page/slug disappears and the new one appears automatically as long as
  it clears `generate_brand_pages.py`'s `MIN_PRODUCTS` (3) threshold.
- **This is a customer-visible change.** Per this repo's branch
  discipline (`CLAUDE.md`), don't push a removal/relabel/update straight
  to `main` without the owner's explicit OK — stage it on a branch first
  unless told otherwise.

### 5. Document
Commit message (and/or `STAGED_UPDATES.md` entry) with exact counts:
checked X of Y live, N kept-and-updated, N kept-from-PDF, N removed, N
flagged for the owner. This is what let a later audit (none yet, but
see `reference.md`) start from "what's changed since last time" instead
of a cold re-check — keep it up.

## Non-negotiables (inherited, not new)

- Never fabricate data for a field you couldn't verify.
- Never guess at a brand-identity correction — confirm with the owner.
- Never remove on the strength of one unchecked source.
- Price ambiguity gets flagged, not resolved by guessing.
