# Souvenier Giftos — Client Catalog

Public, client-facing static corporate-gifting catalog site. Browse
categories/brands/kits, build a shortlist, send a quote via WhatsApp.
Deployed via GitHub Pages from `main` (root) —
https://arsalannaqvi.github.io/souvenier-giftos-catalog/. See `README.md`
for the deploy-history note (moved off Netlify 2026-10-07).

**This is a deliberately slim public mirror.** The business's internal
working repo — Notion-based product intake, the scraping/extraction
engine, pricing/categorization rules, lead-gen — is a **separate, private
repo (`Gifting-automation`)**. If a task is about scraping a supplier site,
writing to Notion, or lead generation, it belongs there, not here. This
repo only holds the customer-facing catalog and the price-refresh
automation that keeps its prices current (see `.claude/skills/
livepriceupdate/SKILL.md`).

## Architecture — three separate page types, no shared JS runtime

There is no SPA router and no build step. Three distinct HTML/JS pairs,
each its own `(() => { ... })()` IIFE with its own duplicated
`STORAGE_KEYS` object (by design — see "Shared state across pages" below,
don't try to extract a shared module without a real build step to back it):

- **`index.html` + `js/app.js`** (~2000 lines) — the main browsing
  experience: search, category/brand filters, budget chips, "Shop by Kit",
  the shortlist sheet, the quote form, WhatsApp message composition.
- **`product/<id>/index.html` + `js/product.js`** — one static page per
  product (2,959 of them), generated by `scripts/generate_product_pages.py`.
  Gallery, colours/sizes, related products, records "recently viewed."
- **`brand/<slug>/index.html` + `js/brand.js`** — one static page per
  brand with 3+ products, generated by `scripts/generate_brand_pages.py`
  (wipes and regenerates the whole `brand/` dir every run — a renamed or
  removed brand propagates cleanly, nothing orphaned).
- `js/logo-editor.js` — the on-page logo-placement preview tool
  (`index.html` only).

**Every product/brand page embeds its own data inline** as
`window.__PRODUCT__`/`window.__BRAND__` JSON, baked in at generation time.
This means **editing `data/products.json`, `data/brands.json`, or
`data/kits.json` does nothing to the live static pages until you re-run
the generator scripts**:
```
python3 scripts/generate_product_pages.py
python3 scripts/generate_brand_pages.py
```
Run both after any data edit, even a small one — forgetting this is the
single easiest way to ship a change that works on `index.html` but silently
doesn't show up on product/brand pages (they'd still show the old baked-in
JSON). `generate_product_pages.py` generates unconditionally for every
product, including `hideFromCatalog: true` ones (deliberate — see below).

## Cache-busting — bump on every JS content change

Each JS file is loaded with a `?v=YYYYMMDDHHMM` query string
(`index.html`'s `<script src="js/app.js?v=...">`, and the equivalent
inside `generate_product_pages.py`/`generate_brand_pages.py`'s HTML
templates for `product.js`/`brand.js`). **Bump the version string whenever
you change that JS file's content**, in its template/source location, then
regenerate product/brand pages — otherwise a browser with a cached copy
keeps running the old JS indefinitely. There's no other cache invalidation
mechanism on this static site.

## Data model

- **`data/products.json`** — `{"categories": [...], "products": [...]}`,
  ~2,959 products. Core fields: `id`, `category`, `name`, `price`, `image`,
  `images[]`, `subcategory`, `sourceUrl`. Two known-stale/unused leftover
  fields on many records: a per-product `href` (navigation is always
  computed fresh as `product/${id}/`, this field is ignored) and the
  entire separate `data/productDetails.json` file (nothing in the
  codebase reads it — `grep` confirms zero references; its fields
  `description`/`subcategory`/`colours`/`sizes`/`images` were at some
  point merged directly into `products.json` itself instead). Don't edit
  `productDetails.json` expecting it to do anything.
- **`data/brands.json`** — flat `{productId: brandName}` map. **This is a
  SEPARATE source of truth from the brand name embedded in a product's own
  `name` string** — e.g. a product literally named "TTH Formal Shirt" can
  map to brand `"Botanica"` here if that's what the owner confirmed is
  actually correct. Fixing a brand requires editing BOTH this file (for
  the brand filter/brand pages) AND, if the name string itself is also
  wrong, `products.json`'s `name` field — missing either one leaves a
  stale value visible somewhere (confirmed the hard way during the
  2026-10-30 TTH→Botanica relabel, see git history on `gifting-workflow`).
- **`data/kits.json`** — curated multi-product bundles for "Shop by Kit":
  `[{id, name, productIds: [...]}]`. Rendered entirely client-side
  (thumbnails/contents/price total computed from `productIds` looked up
  against `state.products` — nothing else needs to be stored per kit).
  Extra fields beyond `id`/`name`/`productIds` are safely ignored by the
  renderer (used for `auto`/`generatedAt` bookkeeping on the 8
  algorithmically-generated kits added 2026-10-30 — see git log).
- **`data/config.json`** — `businessName`, `tagline`, `salesTeam`
  (name+WhatsApp number per rep, shown as the "send to" picker),
  `currency`, `showPrices`, `clients`.
- **`hideFromCatalog: true`** (added 2026-10-30) — a per-product flag,
  NOT deletion. Hides a product from every customer-facing browsing
  surface (client-side filter in `app.js`'s `state.products` assignment,
  AND a separate filter in `generate_brand_pages.py`'s product-grouping
  step, since brand pages are static and bypass the client-side JS
  entirely — **both places need the filter, missing either one leaves the
  product visible somewhere**). Deliberately does NOT filter: individual
  product pages (still generated, harmless — no `sitemap.xml`/
  `robots.txt` exists, so no indexing risk) or the price-check scripts
  (a hidden product should still get price-tracked in case it's
  unhidden later). Currently 83 products hidden — raw PC-building/
  IT-ops hardware (gaming cases, CPU fans, PSUs, barcode scanners, bulk
  cable packs) that had no business being in a corporate-gifting catalog;
  see the commit on `gifting-workflow` for the full category breakdown.

## Enquiry flow — WhatsApp only, no backend

There's no server and no form backend (Netlify's was lost in the GitHub
Pages move, see README). A client builds a shortlist, fills a quote form
client-side, and `js/app.js` composes a formatted message opened via a
`wa.me/<number>?text=...` deep link to one of `config.json`'s
`salesTeam` numbers. Nothing is ever submitted anywhere except that
WhatsApp link.

**Enquiry source tagging** (`?src=<label>` query param, added 2026-10-30):
share a link like `/?src=instagram-bio` or `/brand/coconut/?src=email-
newsletter` and that label rides along into the eventual WhatsApp message
footer. Captured independently in `app.js`/`product.js`/`brand.js` (same
`wa-catalog:enquiry-src` localStorage key, 7-day freshness window, last
tagged click wins) since a client can land on any of the three page types
first — see each file's `captureEnquirySource()`.

**Shared state across pages**: several localStorage keys
(`wa-catalog:shortlist`, `wa-catalog:recently-viewed`, `wa-catalog:
enquiry-src`) are deliberately duplicated as literal string constants in
all three JS files instead of imported from one place, because there's no
build step to make a real shared module work across `index.html`,
`product/*/index.html`, and `brand/*/index.html` as independent static
pages. Keep the key strings in sync by hand if you ever rename one.

## Price automation

`.github/workflows/daily-price-check.yml` runs a live price-verification
pass on a cron (and on-demand). Full tiered protocol (Tier A/B/C, cost
ladder, per-domain calibration log, the MRP-vs-sale-price bug, a weekly
Saturday 🔴-tier schedule) is documented in
`.claude/skills/livepriceupdate/SKILL.md` — read that before touching
anything price-related rather than re-deriving it here.

## Two tracking files with an unreconciled overlap

- **`STAGED_UPDATES.md`** — a Pending/Shipped log, originally assuming all
  work lands directly on `main`.
- As of 2026-10-30, a block of catalog-UX work (hideFromCatalog, enquiry
  source tagging, 2 mobile-layout bug fixes, 8 auto-generated kits) was
  built and pushed to a **separate `gifting-workflow` branch**, not
  merged to `main` and not logged in `STAGED_UPDATES.md`'s Pending
  section. **These two facts don't currently agree with each other** —
  whoever merges `gifting-workflow` should decide whether to log those
  items into `STAGED_UPDATES.md` retroactively or treat git history on
  that branch as the record instead. Not resolved here; flagging so a
  future session doesn't assume `STAGED_UPDATES.md` "Pending (0)" means
  nothing is actually in flight.
- **Branch discipline**: don't push a customer-visible/live-site-facing
  change straight to `main` without the owner's explicit OK — this was
  the standing instruction for the 2026-10-30 work above, not written
  down anywhere before now.

## Testing

Playwright/Chromium is pre-installed in this session's cloud environment
(`/opt/pw-browsers/chromium` — pass `executablePath` explicitly, don't
run `playwright install`). No existing test suite; verification so far has
been manual: serve the repo root (`python3 -m http.server <port>`) and
drive a real mobile-viewport (`devices['iPhone 13']`) browser through the
actual UI — add to shortlist, open sheets, check for off-screen/clipped
elements by comparing a DOM element's `getBoundingClientRect()` against
`window.innerWidth`, not just eyeballing a screenshot. See the
2026-10-30 mobile-pass commit on `gifting-workflow` for the pattern (it
caught a real off-screen filter input this way, which a screenshot alone
made easy to miss at a glance).

## `.claude/agents/`

Two lightweight subagents for routine, mechanical work on this repo —
see each file's own description for exactly when to reach for it instead
of doing the work directly:
- `haiku-scout.md` — read-only lookups (product/brand/kit lookups,
  checking what's already in a data file, confirming a count or a
  category list) that don't need judgment calls.
- `haiku-worker.md` — small, fully-specified mechanical edits (apply an
  already-decided batch of field changes, run the generator scripts,
  simple structural JSON edits) where the *what to change* has already
  been decided and doesn't need re-deciding by the agent.

Neither is a substitute for reasoning through an ambiguous or judgment-
heavy task (brand attribution, kit curation, bug diagnosis) yourself —
those stay in the main session, same as every example in this file's own
git history above.
